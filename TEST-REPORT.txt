LOCALCODE - RELEASE VERIFICATION POLICY / PRUEFREGELN

Source of truth
---------------
This tracked file intentionally contains no frozen PASS timings, executable hashes,
or historical coverage percentages. Those values become stale as soon as source code
changes. The authoritative verification result for a commit is the GitHub Actions
`Quality` workflow for that exact commit SHA. Release artifacts and hashes are produced
by the tag-driven `Release` workflow.

Required Quality gates
----------------------
A commit is release-ready only when all of these checks pass on Windows:
- Go version/setup matches the supported Go 1.25 toolchain.
- `gofmt` reports no unformatted Go source.
- `go vet ./...` passes.
- Frontend JavaScript syntax checks pass for `i18n.js` and inline scripts in the
  desktop and Remote HTML applications.
- `govulncheck` reports no reachable known Go vulnerability that fails the gate.
- The real loopback HTTP integration test passes through Desktop HTTP, Settings,
  Remote pairing, authenticated Remote status, one-time SSE stream-ticket issuance,
  SSE connection, and stream-ticket replay rejection.
- The complete Go test suite passes.
- The Go race detector passes.
- Atomic statement coverage is at least 80.0%.
- Native Windows GUI and diagnostics executables build successfully.
- `git diff --check` passes.

Security regression expectations
--------------------------------
The test suite includes behavior assertions for the hardened boundaries added in the
production-quality hardening branch, including:
- canonical project sandbox containment across symlinks and NTFS junctions;
- conservative approval handling for free-form shell commands and structured tools;
- Git read-only classification and exact persistent Git approval patterns;
- Remote opt-in/loopback defaults, pairing attempt limits, short pairing lifetime,
  device-token expiry/revocation, sanitized device responses, and one-time SSE tickets;
- Remote credentials isolated from the generic Settings API;
- subscriber/event concurrency safety;
- serialized configuration mutation and corruption recovery;
- chat-history last-known-good recovery;
- external MCP servers disabled by default, version-pinned, and lazily initialized;
- `stage_all=false` behavior and Unicode-safe commit-message handling.

Test naming
-----------
`scripts/ui-e2e-test.py` is a mocked browser/UI smoke test. It is not the source of
truth for backend integration. Real Desktop/Remote network integration is covered by
the Go loopback HTTP integration test in the Quality workflow.

Release verification
--------------------
The tag-driven `Release` workflow must additionally:
- require the Git tag to match `VERSION.txt`;
- run the Windows test/build path;
- create `LocalCode.exe` and `LocalCode-Debug.exe`;
- generate SHA-256 checksums and build metadata;
- produce artifact attestations where supported;
- publish the GitHub Release only after successful verification.

Remaining operational controls
------------------------------
- `master` should be protected in GitHub and require the `Quality` check before merge.
- Phone Remote is disabled and loopback-bound by default. If LAN binding is explicitly
  enabled, the current transport is HTTP; use it only on a trusted local network until
  a TLS transport boundary is implemented.
